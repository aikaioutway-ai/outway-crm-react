# Бизнес-правила (деньги)

Каждое правило ниже перепроверено по актуальному коду (`utils/pricing.ts`, `services/financeService.ts`, `services/crmV2Service.ts`, `supabase/functions/daily-penalty/index.ts`, `types/index.ts`), а не переписано из CLAUDE.md вслепую. Там, где код не подтверждает деталь однозначно — помечено отдельно.

## Тарифы по школам и зонам

**Что происходит:** цена ребёнка = тариф школы по зоне (A/B/C), либо фиксированная цена для альтернативного транспорта (минивэн/седан) — не зависит от школы.

**Где реализовано:** `utils/pricing.ts` → `PRICE_RULES` (таблица школа → {zone1, zone2, zone3}) и `getPriceByZone()`.

- Минивэн — 9500 сом/мес, седан — 10500 сом/мес, вне зависимости от школы и зоны.
- Иначе — берётся `zone1`/`zone2`/`zone3` конкретной школы; если для зоны C тарифа нет (`zone3 = null`), используется тариф зоны B.
- Зона по расстоянию (`getZoneByDistance`): ≤3.3 км → A, ≤6.3 км → B, свыше — C.

Список тарифов по каждой из 19 школ в `PRICE_RULES` — актуален на момент проверки, но это живая настройка, а не архитектурный факт: при изменении цен смотреть сам файл, а не эту таблицу.

## Скидка на второго и следующих детей

**Что происходит:** второй и последующие дети в семье получают скидку 5% от их собственного базового тарифа (не от общей суммы).

**Где реализовано:** `utils/pricing.ts` → `getChildPrice(kid, index)`: `index === 0` — полная цена, `index > 0` — `base * 0.95`. Сверху может дополнительно применяться индивидуальная скидка (`discountType: 'percent' | 'fixed'`).

**⚠️ Уточнение:** эта функция (`getChildPrice`/`getFamilyPrice`) нигде не вызывается в `src/` за пределами `pricing.ts` и его теста. В реальности цена и скидка каждого ребёнка хранятся как отдельные колонки в `v2_children` (`base_price`, `sibling_discount_percent`, `manual_discount_percent`, `manual_discount_amount`, `final_price`) и выставляются через UI (`FamiliesPage.tsx`, `InlineFamilyCard.tsx`), который использует только `getPriceByZone()`, а не `getChildPrice`/`getFamilyPrice`. **ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** применяется ли правило "5% на второго ребёнка" сейчас автоматически где-то в UI/RPC, или скидка `sibling_discount_percent` выставляется вручную по каждому ребёнку без автоматического расчёта. Из просмотренного кода однозначно подтвердить автоматическое применение 5% нельзя.

## Депозит = май

**Что происходит:** депозит — это цена семьи за один месяц, который "закрывает" последний месяц учебного года (май) — отдельно за май платить не нужно, если внесён депозит.

**Где реализовано:** `financeService.ts`, с буквальным комментарием в коде `// депозит хранится как май`:
- Ввод депозита в UI (`periodMonth = 0`) сохраняется в БД как `period_month = 5`.
- У депозита `charge_type = 'deposit'`; у самостоятельного начисления за май — отдельный `charge_type = 'may'` (не `'monthly'`).
- И депозит, и майское начисление списываются из отдельного кошелька `wallet_type = 'deposit'` (не из основного `main`) — это и есть механизм, которым депозит "закрывает" май.

Это полностью подтверждено кодом, включая явный комментарий разработчика — самое надёжное правило в этом документе.

## Пеня

**Что происходит:** до 5-го числа пеня не начисляется; начиная с 6-го — плюс 100 сом в день; потолок — 15% от суммы долга; во время статуса "На проверке" пеня не растёт (заморожена).

**Где реализовано:** **не в клиентском коде.** Формула продублирована в `utils/pricing.ts` (`calcPenalty`), но эта функция нигде не используется. Фактическое начисление — server-side, в Supabase Edge Function `supabase/functions/daily-penalty/index.ts`, вызываемой по расписанию cron `0 8 7-31 * *` (каждый день с 7 по 31 число в 08:00):

- `PENALTY_PER_DAY = 100`, `PENALTY_MAX_PERCENT = 0.15` — совпадает с описанием.
- Пеня не трогает начисления со статусом, отличным от `unpaid`/`partial`, и с `is_frozen = true`.
- Есть защита от повторного начисления в один день (`penalty_last_charged_on`).

**ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** функция читает/пишет колонки `penalty_amount`, `is_frozen`, `penalty_last_charged_on` на таблице `v2_charges`, но в найденном в репозитории определении `v2_charges` (`crm_v2_schema.sql`) колонок `penalty_amount`/`is_frozen` нет — они описаны только в схеме старой неиспользуемой таблицы `charges`. Похоже, эти колонки были добавлены на живую `v2_charges` вручную (не отслеживаемой миграцией), как это явно сделано для `penalty_last_charged_on` в `supabase/v2_charges_penalty_idempotency.sql`. Само поведение (100/день, потолок 15%, заморозка) подтверждено кодом функции; точное определение колонок в БД — нет.

Также: cron стартует с 7-го числа, а не с 6-го — то есть при выключенном ручном запуске первое реальное начисление физически произойдёт 7-го, хотя код формально разрешил бы его и на 6-м.

## Статусы — два независимых уровня, не путать

В `types/index.ts` определены два разных статусных набора, и они не одно и то же:

- **`PaymentReviewStatus`** (статус самого платежа от семьи): `Черновик` → `На проверке` → `Подтверждено` / `Отклонено`. В БД (`v2_payments.status`) это `pending` / `confirmed` / `rejected` / `cancelled`.
- **`PaymentStatus`** (статус начисления/долга ребёнка за период): `Не оплачено`, `Частично оплачено`, `Оплачено`, `Просрочено`, `Заморожено`. В БД (`v2_charges.status`) это `unpaid` / `partial` / `paid` / `overpaid` / `cancelled`.

**Расхождение:** значения `Просрочено` и `Заморожено` есть в типе `PaymentStatus` на клиенте, но в перечислении допустимых значений `v2_charges.status` в схеме их нет (там нет `overdue`, заморозка выражена отдельным булевым полем `is_frozen`, не статусом). Похоже, "Просрочено" — это лейбл, который UI показывает поверх статуса `unpaid` при определённых условиях (например, прошёл срок), а не отдельное значение, реально хранимое в базе. **ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** где именно и по какому условию вычисляется переход в "Просрочено" на клиенте — в изученных сервисах (`financeService.ts`, `crmV2Service.ts`) явного вычисления не найдено, а прямого использования строки `'overdue'` в них тоже нет.
