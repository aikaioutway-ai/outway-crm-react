# Бизнес-правила (деньги)

Каждое правило ниже перепроверено по актуальному коду (`utils/pricing.ts`, `services/financeService.ts`, `services/crmV2Service.ts`, `types/index.ts`), а не переписано из CLAUDE.md вслепую. Там, где код не подтверждает деталь однозначно — помечено отдельно.

**Пеня как бизнес-правило OutWay CRM больше не используется** (подтверждённое решение пользователя). Раньше здесь описывалась логика начисления через Edge Function `daily-penalty` — сама функция, связанные поля (`penaltyAmount`, `isFrozen`) и helper `calcPenalty` удалены из кодовой базы.

## Тарифы по школам и зонам

**Что происходит:** цена ребёнка = тариф школы по зоне (A/B/C), либо фиксированная цена для альтернативного транспорта (минивэн/седан) — не зависит от школы.

**Где реализовано:** `utils/pricing.ts` → `PRICE_RULES` (таблица школа → {zone1, zone2, zone3}) и `getPriceByZone()`.

- Минивэн — 9500 сом/мес, седан — 10500 сом/мес, вне зависимости от школы и зоны.
- Иначе — берётся `zone1`/`zone2`/`zone3` конкретной школы; если для зоны C тарифа нет (`zone3 = null`), используется тариф зоны B.
- Зона по расстоянию (`getZoneByDistance`): ≤3.3 км → A, ≤6.3 км → B, свыше — C.

Список тарифов по каждой из 19 школ в `PRICE_RULES` — актуален на момент проверки, но это живая настройка, а не архитектурный факт: при изменении цен смотреть сам файл, а не эту таблицу.

## Скидка на второго и следующих детей

**Что происходит:** первый ребёнок семьи — 0% скидки; второй и каждый последующий — автоматически 5% скидки от собственного базового тарифа (не от общей суммы). Правило применяется независимо от способа появления ребёнка в системе.

**Где реализовано (два независимых, но согласованных места):**
- **Первичная регистрация через форму:** `project/apps-script/outway-crm-import-webapp.gs` → `syncToSupabaseV2_()` — `siblingDiscount = index === 0 ? 0 : 5` по порядку детей в заявке.
- **Добавление ребёнка через CRM:** `src/modules/families/InlineFamilyCard.tsx` → `addDraftChild()`, использует `getSiblingDiscountPercent(index)` из `utils/pricing.ts`, где `index` — количество уже существующих в семье детей (сохранённых + добавленных в этой же сессии редактирования) на момент добавления нового.
- Формула цены в обоих местах одинаковая: `finalPrice = round(basePrice * (1 - discount / 100))`.

**Приоритет скидок (не складываются):** если менеджер вручную выставил `manualDiscountPercent`, используется он; `siblingDiscountPercent` — только запасной вариант, когда ручной скидки нет (`manualDiscountPercent || siblingDiscountPercent || 0`, см. `InlineFamilyCard.handleSaveChild`). Это правило не менялось.

**Важно:** при добавлении ребёнка через CRM цена/скидка фиксируются один раз в момент создания. Если после этого поменять зону/транспорт черновика ребёнка до сохранения — цена не пересчитывается автоматически (это существовавшее ограничение, не связанное со скидкой, из этой задачи не устранялось).

Массового пересчёта уже существующих в БД детей это правило не затрагивает — оно действует только при создании/добавлении нового ребёнка.

## Депозит = май

**Что происходит:** депозит — это цена семьи за один месяц, который "закрывает" последний месяц учебного года (май) — отдельно за май платить не нужно, если внесён депозит.

**Где реализовано:** `financeService.ts`, с буквальным комментарием в коде `// депозит хранится как май`:
- Ввод депозита в UI (`periodMonth = 0`) сохраняется в БД как `period_month = 5`.
- У депозита `charge_type = 'deposit'`; у самостоятельного начисления за май — отдельный `charge_type = 'may'` (не `'monthly'`).
- И депозит, и майское начисление списываются из отдельного кошелька `wallet_type = 'deposit'` (не из основного `main`) — это и есть механизм, которым депозит "закрывает" май.

Это полностью подтверждено кодом, включая явный комментарий разработчика — самое надёжное правило в этом документе.

## Статусы — два независимых уровня, не путать

В `types/index.ts` определены два разных статусных набора, и они не одно и то же:

- **`PaymentReviewStatus`** (статус самого платежа от семьи): `Черновик` → `На проверке` → `Подтверждено` / `Отклонено`. В БД (`v2_payments.status`) это `pending` / `confirmed` / `rejected` / `cancelled`.
- **`PaymentStatus`** (статус начисления/долга ребёнка за период): `Не оплачено`, `Частично оплачено`, `Оплачено`, `Просрочено`, `Заморожено`. В БД (`v2_charges.status`) это `unpaid` / `partial` / `paid` / `overpaid` / `cancelled`.

**Расхождение:** значение `Просрочено` есть в типе `PaymentStatus` на клиенте, но в перечислении допустимых значений `v2_charges.status` в схеме его нет (`overdue` не входит в constraint) и нигде в коде оно фактически не вычисляется. **ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ:** является ли это запланированной, но нереализованной функциональностью, или лишний элемент типа, который можно убрать.

`Заморожено` соответствует DB-статусу `cancelled` на `v2_charges` — это отдельный, самостоятельный статус начисления (например, начисление аннулировано), не связанный с пеней и не требующий отдельного булевого поля.
