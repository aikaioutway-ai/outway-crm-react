# OCR чеков и защита от повторной отправки

## Извлечение

Anthropic Haiku извлекает банк, сумму без комиссии, дату операции, время с исходной точностью, последние четыре цифры счёта/карты отправителя и код чека. Правила содержат форматы Optima, Bakai, DemirBank и MBANK. Это настройка запроса и проверки результата, а не обучение весов модели.

Время телефона, реквизиты получателя и дата загрузки не используются. Для Optima `mbiz:` сохраняется как код, но не считается уникальным ID. Отсутствующие данные остаются пустыми и доступны для ручного заполнения.

Локальный сервер использует `ANTHROPIC_API_KEY` из `.env.local` или окружения; после изменения нужен перезапуск. Прежний `VITE_ANTHROPIC_API_KEY` поддерживается для совместимости. Без ключа отправка OCR даёт понятную ошибку 503.

## Дубли

Перед загрузкой файла CRM вычисляет SHA-256 его байтов и вызывает `find_receipt_duplicate`. Ошибка проверки останавливает отправку. Изменение имени файла не меняет хеш; пересъёмка/перекодирование меняет.

Проверка ищет среди всех семей платежи `pending` и `confirmed` по:

- одинаковому SHA-256;
- уникальному UUID/QR/MBIZ_S-коду либо номеру квитанции с известным банком;
- одинаковым банку, сумме, дате, времени и четырём цифрам счёта отправителя.

Если один чек содержит только минуты, сравнение времени допускает ту же минуту. Это совпадение реквизитов, а не банковское подтверждение. Перед повторной отправкой следует сверить данные и выписку. Сам по себе одинаковый `mbiz:` не блокирует разные платежи. Отклонённый платёж можно отправить заново.

Серверный триггер на `v2_payments` повторяет проверку при записи. Проверки сериализованы advisory lock; активные файловые хеши дополнительно защищены уникальным индексом. Настройки прав доступа не расширялись: функции работают как SECURITY INVOKER с существующими политиками.

Сообщение о дубле содержит исходный платёж, семью, дату и сумму. Черновик формы остаётся заполненным.

## Проверка базы 21.10.2026

На момент аудита: 1954 платежа, 1892 с кодом; банк/время/последние цифры у старых записей не заполнены. Обнаружено 13 групп одинаковых уникальных кодов среди `pending`/`confirmed`. Исторические записи не удалялись и не менялись.

Старые чеки Optima без уникального ID и метаданных нельзя надёжно проверить по одному `mbiz`. Для полного исторического покрытия нужен отдельный проход по старым файлам: хеширование и распознавание реквизитов.

Проверки в реальной БД: существующий код Demir отклонён; один файл у разных семей отклонён; совпадение реквизитов Optima отклонено; общий `mbiz` с разными реквизитами принят. Все тестовые записи откатились в под-транзакции.

Исходник Telegram-бота обновлён для тех же полей и проверок. В проекте Supabase на момент проверки нет развёрнутой функции `telegram-bot`; новый бот автоматически не публиковался.
